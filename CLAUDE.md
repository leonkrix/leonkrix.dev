# leonkrix.dev

Personal portfolio website of **Leon Krix, Software Engineer**. Live at https://leonkrix.dev.
Goal: a modern, minimal, dark, best-practice developer portfolio with subtle animations, a small games section and a few easter eggs. Static site, no backend.

The roadmap lives in [PLAN.md](PLAN.md). Work through it phase by phase; do not jump ahead into games or extras before the MVP is live.

## CI/CD (GitHub Actions is mandatory)

We always use **GitHub Actions**. **Nothing is deployed unless CI is green.** This is a hard rule, not a nice-to-have.

### CI (`.github/workflows/ci.yml`)

Runs on every pull request and on pushes to `main`. Structure: a reusable composite action `.github/actions/setup` (pnpm + Node from `package.json`/`.nvmrc`, cached, `pnpm install --frozen-lockfile`, `HUSKY=0`), parallel jobs, and one aggregate job `ci-ok` ("CI passed") that `needs` all others. **Branch protection requires only `ci-ok`**, so new jobs are added to its `needs` list without touching repository settings.

Jobs (all live):

1. `quality` (live): `pnpm lint`, `pnpm format:check`, `pnpm typecheck` (`astro check`)
2. `test` (live): `pnpm test` (Vitest)
3. `build` (live): `pnpm build` (without the contact form, like production before the switch), `pnpm test:dist` and `pnpm build:functions` (the Cloudflare Functions must bundle with the Workers settings)
4. `site-checks` (live, part of the `build` job): `pnpm test:dist` runs Vitest checks against the build output in `dist/` (see Testing strategy)
5. `e2e` (live): Playwright against the production build with the contact form built in (`pnpm build:form`; the API is answered by `page.route`) (desktop and mobile), see `tests/e2e/`: smoke tests, privacy guard (same-origin only, no cookies) and axe accessibility scans. The shared fixture fails every test on console errors, CSP violations and HTTP errors. On failure the HTML report is uploaded as an artifact
6. `lighthouse` (live): `pnpm lighthouse` runs `scripts/lighthouse.mjs`: Lighthouse (mobile) three times against the production build with the contact form built in, median, every category at least 95, transfer budgets (scripts 10 KB, stylesheets 20 KB, total 200 KB, measured with the uncompressed preview server) and no request to another origin. It also tests `/games/` and every game page that exists in `dist/`; a game page uses its own budget from `GAME_BUDGETS` in the script (no entry, no run). Needs a Chrome (set `CHROME_PATH` if it is not found); the CI uses the runner's preinstalled one. Lower a limit only with a reason, raise the budgets only deliberately
7. `actionlint` (live): lints the workflow files; the binary is pinned by version and SHA-256 checksum (bump both together, Dependabot cannot update it)
8. `dependency-review` (live, pull requests only, fails on high severity; skipped on pushes, which does not fail the gate)
9. `audit` (live): `pnpm audit --audit-level high` fails on known high or critical vulnerabilities in any dependency. Because a newly published CVE can turn it red without any code change, it also runs weekly; an unfixable finding is recorded with a reason in pnpm's audit configuration instead of weakening the check

Separate workflows (not part of the `ci-ok` gate at first, findings show as PR checks and in the Security tab): **CodeQL** (live: `codeql.yml`, requires that the repo setting "Code scanning default setup" is NOT enabled, otherwise the two conflict) (`javascript-typescript`, on PRs, `main` and weekly) in `.github/workflows/codeql.yml`, and **OpenSSF Scorecard** (live: `.github/workflows/security.yml`, on pushes to `main`, weekly and on branch protection changes; results are published for the README badge and uploaded to the Security tab; the same workflow runs the weekly audit). `SECURITY.md` and private vulnerability reporting are enabled.
**SonarQube Cloud is deliberately not used**: it overlaps almost entirely with ESLint, strict TypeScript and CodeQL, does not create PRs, and needs an external account plus a token secret. Revisit only as an experiment.

### Testing strategy

Tests exist to protect what would actually hurt: broken pages, legal pages missing, accessibility/performance regressions, privacy leaks, and broken game logic. Not to hit coverage numbers.

- **Unit (Vitest)**: pure game logic (Wordle evaluation, daily word from date, dictionary validation, Clueless ranking), utilities, content schemas. Word lists get data tests (length, lowercase, no duplicates, valid characters).
- **Content validation**: Zod schemas on content collections so bad data fails the build (e.g. private projects must not carry a repo link).
- **Build-output checks (Vitest over `dist/`)**: every page has `<title>`, meta description, canonical, `lang`; `/legal-notice` and `/privacy-policy` exist (both languages, same sections) and are linked from the footer of every page, and the old German addresses redirect; `robots.txt` and `sitemap.xml` exist; no broken internal links; no `http://` resources; Impressum placeholders are not left in production output.
- **Privacy guard (Playwright)**: assert that page loads make requests only to our own origin (no third-party fonts/scripts/embeds), set no cookies and leave local storage, session storage, IndexedDB, cache storage and service workers empty. This protects the "no cookie banner" decision and the privacy policy statement that nothing is stored on the device. A build-output test scans our source and the published JavaScript for those APIs as early warning (allow-list for libraries in the test, with a reason).
- **E2E smoke (Playwright)**: home loads, header anchors scroll to sections, mobile viewport, each game can be played with the keyboard, keyboard navigation, reduced-motion respected, no console errors.
- **Accessibility**: `@axe-core/playwright` scan of every page, fail on violations.
- **Performance/SEO**: Lighthouse CI budgets plus a JS bundle size budget.
- **Security hygiene**: `pnpm audit`, dependency review, CodeQL, secret scanning (public repo, so GitHub secret scanning and push protection are enabled).
- Not planned: visual regression snapshots (high maintenance for low value on a personal site), coverage thresholds.

### Gating deployment behind CI

Decision: **Cloudflare's Git integration deploys, GitHub Actions runs CI in parallel, and branch protection makes CI the gate.** We deliberately do NOT deploy from Actions (no API token, no wrangler-action): it is more moving parts and secrets for no benefit on a static site.

- Cloudflare deploys only `main` to production and builds pull requests as (non-public) preview deployments.
- **Branch protection on `main`** is what enforces the rule: pull requests required, all CI status checks required and green, branch must be up to date before merge, no force pushes, no direct pushes. Since only CI-verified code can reach `main`, production is effectively gated by CI.
- Preview builds run in parallel with CI; that is fine, previews are not production. The CI checks still block the merge.
- **Build budget**: production builds happen only when a PR is merged into `main`. Preview builds are triggered by pushes to branches/PRs and count against Cloudflare's free build allowance. So: commit as often as you like locally, but **push a feature branch when the feature is complete** (or open a draft PR), one branch per complete feature. Restrict preview builds in the Cloudflare project's branch control if needed. GitHub Actions minutes are unlimited for public repos, so CI runs are not a concern.
- Dependabot PRs are grouped weekly to limit preview builds.
- No Cloudflare API token or other deploy secrets are needed. Never commit secrets or tokens.
- Workflow hygiene: minimal `permissions:` per workflow/job, pin third-party actions to a full commit SHA (Renovate/Dependabot keeps them updated), `concurrency` groups to cancel superseded runs, cache pnpm store.
- **Dependency updates**: Dependabot opens PRs every Monday (npm and GitHub Actions): one grouped PR for all minor and patch updates, major updates alone, at most 5 open. Dependabot alerts and security updates are on (GitHub opens a fix PR as soon as a vulnerability is published). Merge rule: green CI is necessary, not sufficient. Merge grouped minor/patch PRs with "Squash and merge", then `git pull` and `pnpm install`. Majors need a look: they are ignored for `typescript` (no TS 7 support in the tooling yet), `eslint` and `@eslint/js` (plugins verified up to the current major) and `@types/node` (must match the Node major in `.nvmrc`; bump all together).
- **A red audit after a merge is normal sometimes:** `pnpm audit` checks the lockfile against the advisory database _of that moment_. A PR can be green on Monday and the same files red on Tuesday, because an advisory was published in between (this happened twice). Fix: update the vulnerable package inside its allowed range (`pnpm update <name>`, lockfile only), or, when a dependency pins the vulnerable version exactly and upstream has no fix yet, add an entry to `overrides` in `pnpm-workspace.yaml` with a comment saying why and when to remove it (none at the moment: the `sharp` override was removed on 2026-10-14, because miniflare inside wrangler asks for sharp 0.35.5 itself now). Overrides are written as a range of the bad versions (for example `sharp@<0.35.5`), so they apply only while a dependency still asks for a vulnerable version and become inert on their own once upstream moves on; a leftover entry is harmless dead configuration, not a risk. Clean up when convenient: when the package that needed it asks for a safe version itself (look at its `package.json` in `node_modules` or with `pnpm why`), delete the entry, run `pnpm install && pnpm audit`, and keep it deleted if the audit stays green. Check `pnpm audit` after every Dependabot merge.

## Security headers and CSP

- HTTP security headers live in `public/_headers` (served by Cloudflare): HSTS (`max-age=31536000; includeSubDomains`), `nosniff`, `X-Frame-Options: DENY`, strict referrer policy, COOP, permissions policy, `frame-ancestors 'none'`, immutable caching for `/_astro/*`.
- The Content Security Policy is generated by Astro (`security.csp` in `astro.config.mjs`) as a `<meta>` element with hashes: `default-src 'self'`, `object-src 'none'`, `frame-src 'none'`, no external hosts, no `unsafe-inline` for scripts or style elements. The only exception is `style-src-attr 'unsafe-inline'`, needed for the obfuscated contact text (inline `--t` custom property).
- `vite.build.assetsInlineLimit: 0` keeps fonts and scripts as files (no `data:` URIs), which the CSP requires. The only inline scripts are the small runtime that Astro writes for a React island (Playground games); the CSP of the page allows each of them by its hash and a build-output test checks that every inline script is covered.
- Consequences for new features: no third-party scripts, styles, fonts, images or embeds without deliberately extending the CSP and the privacy policy; no Astro `<ClientRouter />` (use the native View Transition API); no inline event handlers. CSP is not applied in `astro dev`: check with `pnpm build && pnpm preview` and the browser console (look for "violates the following Content Security Policy directive").
- `tests/build-output/security.test.ts` guards headers and CSP; extend it when the policy changes.

## Content model

- **Experience** (content collection `experience`, one YAML file per entry in `src/content/experience/`, schema in `src/lib/experience.ts`): education and work, shown in two groups (Education, Work) as a **compact list with icons**, deliberately different from the projects timeline (which has dots and cards). Fields: `type`, `title`, `organization`, optional `unit`, `start`/`end` as `YYYY-MM` (no end means "Present"), `highlights` (1-4), optional `coursework`, optional `relatedProject` (id of a project, renders a link to its card `#project-<id>`). Newest first. Not shown: school (Abitur), final degree grades, non-dev jobs, certificates, and no CV download. Never publish a document with personal contact data.
- **Projects** (content collection `projects`, one YAML file per project in `src/content/projects/`, schema in `src/lib/projects.ts`), shown as a vertical timeline, newest first (by end year, then start year). Fields: `title`, `subtitle`, `kind` (project, bachelor-thesis, master-thesis), optional `institution` (shown next to the kind, e.g. a university), optional `grade` (small badge at the top right of the card, e.g. "1.0", explained as best possible in the German system for screen readers), `start`/`end` year, optional `stats` (1-3 project key figures such as "-47% mean delay", shown as a strip; a grade is not a key figure), `highlights` (1-5 bullets), `technologies` (ids from the registry), `code`, an optional `note` and an optional `art` (the small animated picture on the card, one of `projectArts` in `src/lib/projects.ts`; the pictures are pure CSS and SVG in `src/components/project-art/`, calm, a loop of about ten seconds, hidden from assistive technology, still with reduced motion, paused off screen by a tiny script, on the right of the card on wide screens and as a strip below the subtitle on narrow ones; next to the title and the key figures, or, when a project has no key figures, next to the title and the highlights; a new picture is a new component plus an entry in `projectArts`; every picture uses the viewBox `0 0 240 200` and labels of `font-size: 8.5px` in the mono font so that text is equally big in every card, a test checks it). The Defuze picture is generated: change `scripts/generate-defuze-picture.mjs`, run it, commit the result; a test fails if the file differs from what the script makes).
  - `code.status` is `public` (GitHub URL required and shown), `planned` ("Code coming soon") or `none` ("Private project"). A link is impossible for planned/none (the schema strips it), and a public project needs a github.com URL.
  - To publish a thesis later: change its `code` to `status: public` with the URL.
- Start with placeholder data; real content is swapped in later via the collections only.
- Current projects: this website (public), Defuze (MERN + ML, public), Master thesis (GNN + RL for airborne networks, code planned), Bachelor thesis (Tetrys FEC protocol in C++, code planned), Grade & Study Tracker (2019 Android app, no longer available). Adding a project only needs a new YAML file.

- Hero: an availability badge ("Open to opportunities", green status dot, links to the contact section; controlled by `availability` in `src/lib/site.ts`, set `open` to false to hide it), a short intro with calls to action "View projects" and "Contact" (no CV download).
- Timeline strip above the experience list: `ExperienceTimeline.astro` draws bars from the experience entries (layout in `src/lib/timeline.ts`), desktop only and hidden from assistive technology; the experience schema has an optional `short` label for the bar. Cross-document page transitions were tried and dropped (Chrome logs an unhandled rejection when a transition is aborted, see PLAN.md).
- About facts: `AboutFacts.astro` shows "Now" (what is going on, with the month of the last update, the job search item only while `availability.open` is true) and "Languages" (German native, English fluent). Data lives in `src/lib/site.ts` (`now`, `spokenLanguages`). Keep the Now block current. The footer links to the source code (`siteConfig.repo`).
- **Notes** (content collection `notes`, one MDX file per page in `src/content/notes/`, schema in `src/lib/notes.ts`, the file name is the address `/notes/<slug>/`): short write-ups of how something on the site is made, one problem and how it is solved, with numbers, small figures and the tests that back it up; the page template is `src/pages/notes/[slug].astro`, the overview `src/pages/notes/index.astro`, the text styles `.note-prose` in `global.css`. Fields: `title`, `summary` (40 to 240 characters, the line on the overview and the page description), `tag` (small label such as "Logic · Root Cause"), `group` (`site` or `games`: the overview shows two parts, "The site" and "The games", and Next and Previous stay inside the group), optional `game` (slug of a live game: the "How it is built" panel of that game links to the note, and the note offers "Play"), optional `code` (a folder of the repository, shown as "Read the code" on GitHub), `order` (position inside the group, unique in the group, lowest first), `updated` (YYYY-MM-DD, set it when the text changes). A note is **one narrow column**: running text, figures, steps, key figures, code and tables all have the width of the text (`max-width: 42rem` for every child of `.note-prose`), so nothing sticks out. Building blocks for MDX in `src/components/notes/`: `Figure` (caption), `Steps` (a chain of boxes, `columns`), `Stats`, `DeduceFigure` (made for Root Cause); `Code` colours a block at build time (`<Code lang="ts" code={snippet} />`, where the code is a file `src/content/notes/snippets/<name>.snippet` imported with `?raw`, at most 72 characters per line so that it fits the box without scrolling, both checked by `tests/build-output/notes.test.ts`; code is not written in the MDX file itself because Prettier takes the indentation out of code in MDX when it contains a blank line; highlight.js, a dev dependency: the output is plain text with CSS classes such as `hljs-keyword`, coloured in `global.css`; no script, no inline style; an unknown language fails the build), and every plain Markdown fence goes through `CodeBlock` (monospace, focusable, for axe). Shiki and `rehype-highlight` are not used: Shiki writes inline styles and the Markdown processor of Astro 7 (Sätteri) does not run rehype plugins. **Write what is true and verifiable** (numbers from the code and the tests, real output of the game, not invented), in the first person, English. A note needs: a page in `tests/e2e/pages.ts` (automatic), its own entry in `PAGES` of `scripts/check-links.ts` (it links to GitHub) and `src/content/projects/website.yaml` should keep pointing to the overview. There is a note for every game (Root Cause set tone and depth) and four about the site: "How this site is built" (the overview: the journey of a change, the gate, what the checks look at, what broke), "A page that never moves" (the layout guard), "A contact form without a third party" and "Watching the live site" (the live check and the bot protection that locked it out). Each of the four is in the group `site` and links to the others where they belong. **When the site changes in a way that one of these notes describes (a new CI job, a new check in the live check, a change in the contact form or in the layout guard), update the note in the same PR and its `updated` date.** Figures are made from the real data and functions of the site at build time where possible (`EvaluateFigure` calls the real `evaluateGuess`, `ConflictFigure` reads the real Link Up data and fails the build if it no longer matches, `RadarFigure` and `NearestTable` work out a real Word Radar round with the game's own code), so a picture cannot disagree with the game. A long address in a sentence goes into `<Url>` (it may break at any character, so lines stay full); short code in a sentence is plain inline code. ## Design guidelines

- Dark, minimal, generous whitespace, strong typography. No bright/colorful noise.
- **Palette**: cool blue accent family (blue -> cyan/teal as analogous colors) plus one restrained contrast accent (e.g. warm amber) used sparingly. Tokens (starting point, tune during design phase):
  - bg `#0a0d12`, surface `#11161d`, border `#1e2632`
  - text `#e6edf3`, muted `#8b98a9`
  - accent `#4f8cff`, accent-2 `#22d3ee`, contrast `#f5b642`
- Subtle animation: the background is implemented (`Background.astro`, no script). Principle: **reading text never sits on lines or busy patterns**. Every page has two huge, very soft color fields drifting slowly (fixed, behind everything); only the home page hero adds soft top light and a fine grid from the top right corner that scrolls away with the hero. Pages with a lot of text pass `calm` to `BaseLayout` (legal pages do). **No custom cursor and no cursor light** (tried, felt like a searchlight). Interaction feedback lives on the buttons: `.btn-primary` and `.btn-outline` (lift, glow, sheen, press), use them for every new button or button-like link. The page color lives on `html` so the layers at `z-index: -1` show through, do not give `body` a background. Entry motion: the hero elements use `.hero-in` (staggered with `--i`), content blocks use `.reveal` (time based fade-in when scrolled into view, `Reveal.astro`, hidden only while JavaScript runs and motion is allowed). Put `.reveal` on new content blocks below the first screen; never hide content in a way that stays hidden without JavaScript. Animations that keep their end state (fill mode "forwards") would block hover transforms, so use "backwards" or a final keyframe that equals the normal style. Keep animation lightweight (CSS and a few lines of script), it must not hurt Lighthouse and must honor reduced motion.
- Boxes (cards, forms, notices, icon tiles) get the class `edge`: a faint permanent gradient on the border, only to lift them off the background. Header links use an accent underline for the active section instead of blue text. Never put a hover effect on boxes that are not clickable.
- Widths: running text is limited to `max-w-2xl` (about 70 characters per line, readable). Structured content (technology grid, project cards, experience, the About facts box) uses the full container width (`max-w-5xl`). Forms stay at a moderate width: the Contact section puts the form in a right column next to the text on desktop. New sections follow this rule: text narrow, structure wide, forms moderate.
- Mobile-first, responsive, WCAG AA contrast, full keyboard navigation, visible focus styles.
- Use design tokens; no magic colors or spacing values in components.

## Quality bar

- Lighthouse 95+ in all four categories on mobile (enforced in CI).
- Minimal JS shipped: hydrate islands with `client:visible` / `client:idle`; games are lazy loaded.
- Valid semantic HTML, meta tags, Open Graph images, `sitemap.xml`, JSON-LD (`Person`).
- **Fonts and layout shift:** a page that is mostly text must request its two fonts before the stylesheet is read (`<BaseLayout preloadFonts>`, set by the notes, the legal pages and the Uses page), otherwise the text is first set in the fallback font and again in the real one, breaks differently and the page jumps (Lighthouse measured 0.07 on the notes, and on the slower CI machine that was enough to fall under 95, 2026-10-14). The game pages must **not** preload: their page loads a large file at the same time, and the preload made Lighthouse count it into the first paint (75 instead of 98). `tests/build-output/fonts.test.ts` holds both rules. Lighthouse is sensitive to the order of requests on a page with a big fetch: after any change to what a game page requests, run `pnpm lighthouse` twice and look at the LCP. **Why a score flips (found 2026-10-16, Word Radar, 98 / 89 / 75 / 73 on the same page):** Lighthouse does not time the page, it simulates the run it saw on a slow phone (1.6 Mbit/s, CPU 4 times slower) and counts every request that started before the paint it saw as something that paint waits for. The 2 MB of Word Radar started in the same few milliseconds as the first paint: when it came first the simulation waited for 2 MB (LCP 12.4 s, score 73), when it came after it did not (LCP 1.8 s, score 98); the slower build server made the order random and sometimes partial (89). The rule: **a large request of a page starts only after the page has been painted** (`afterFirstPaint` in `src/games/word-radar/data/load.ts`, guarded by `tests/e2e/word-radar-paint.spec.ts`, which checks that the files start after the first and the largest paint). To look for such a flip run the page 8 to 16 times and print the metrics (FCP, LCP, TBT, CLS, SI) of every run; a median of three hides a flip that happens in one run of four. The weights of the score: TBT 30 %, LCP 25 %, CLS 25 %, FCP 10 %, SI 10 %.
- TypeScript strict, no `any` without justification.
- Unit tests for all game logic; e2e smoke tests for critical paths.

## Legal (Germany) - must stay correct

Not legal advice; have the final texts checked (e.g. eRecht24 / IT-Recht Kanzlei generator).

- **Impressum**: full name, ladungsfaehige Anschrift (no P.O. box), email. Phone is not mandatory if a second fast contact channel exists. Do not cite outdated law (TMG); the current law is DDG. Decision: the **private postal address** is used. It is obfuscated against simple bots as far as possible while staying legally correct (human-readable, no JavaScript required, screen-reader friendly).
  - **Obfuscation approach** (one shared component used by Impressum and Datenschutz): address and phone are never emitted as continuous text in the HTML; they are split into parts and rendered via CSS (`::before { content: attr(data-...) }`), which works without JS and is read by screen readers. The email is assembled from parts (small progressive-enhancement script makes it a clickable link; without JS it stays visible through the CSS output). No images of text (accessibility). A build-output test asserts that the address does not appear as plain text in `dist/`. Additional protection at the edge: Cloudflare Bot Fight Mode, AI-bot blocking and email address obfuscation. Honest limit: a scraper that renders CSS/JS can still read it; this only stops simple crawlers and harvesters.
  - **The postal address is never committed to the repo** (public repo, permanent git history). The repo only contains placeholders plus `.env.example` (`IMPRESSUM_STREET`, `IMPRESSUM_ZIP`, `IMPRESSUM_CITY`, ...). Real values are set as **Cloudflare build variables** and in a local, gitignored `.env`, and are injected into the Impressum page at build time (typed/validated env access via Astro). CI builds use the placeholders. These are not secrets (the address is visible on the live page); the goal is only to keep it out of git history. Name and email may live in the repo.
- Legal pages are **bilingual**: every page has an English version (first) and a German version (second) in one page, with a note at the top that links to both. The **German version is the legally binding original**, the English one is a translation to make it understandable (Art. 12 GDPR asks for clear language for the audience, and the site is English). The addresses are English (`/legal-notice`, `/privacy-policy`; the language of an address is not prescribed, the footer label must be easy to recognize) and the old German ones redirect. Both versions must stay in step: same sections in the same order, same providers. Build-output tests check section numbers, headings and providers in both languages. No phone number is published: the email address and the contact form (once built in) are the two contact channels required by section 5 DDG.
- **Datenschutzerklaerung** (`src/pages/privacy-policy.astro`, text in `src/components/legal/PrivacyPolicyEn.astro` and `PrivacyPolicyDe.astro`, the legal notice in `LegalNoticeEn.astro` and `LegalNoticeDe.astro`; change both languages together): controller, hosting provider (Cloudflare, including third-country transfer note and retention), server logs / IP addresses, the contact form (data incl. the hashed rate-limit counter in Workers KV, purpose, legal basis Art. 6 (1) b/f, the path of the message through Cloudflare to IONOS, recipients, storage period, no obligation to provide data), contact by email, no cookies and nothing stored on the device (section 25 TDDDG), no analytics, external links, TLS, no automated decisions (Art. 22), user rights with the Art. 21 objection notice, supervisory authority (kept generic on purpose: naming the state would reveal the address region), date ("Stand"). Sections are numbered by a counter, and **the contact form section and the Impressum line about the form exist exactly when the form is built in** (`PUBLIC_CONTACT_FORM`), so the text always matches the site; build-output tests check both variants. Retention wording: as long as needed to handle the request, then deleted unless statutory retention applies (section 257 HGB, section 147 AO).
- Cloudflare may set a technically necessary security cookie (`__cf_bm`) when bot protection is on; this is mentioned in the privacy policy. The site itself sets no cookies, so a privacy-guard test must only allow such Cloudflare security cookies.
- **No cookie banner** as long as there are no non-essential cookies, trackers, embeds (YouTube, maps, social widgets) or third-party CDN resources. Adding any of these requires revisiting the privacy policy first.
- No analytics initially. If added later: privacy-friendly and self-hosted (Plausible/Umami) and documented in the privacy policy.
- `robots.txt`: disallow known AI crawlers (GPTBot, CCBot, ClaudeBot, Google-Extended, ...). This is a request, not protection. Real bot protection comes from Cloudflare settings.
- Games: only use word lists, data and assets whose license permits it; record sources in `THIRD_PARTY.md`. The privacy policy says that nothing is stored on the device, so nothing on the site (games included) may use browser storage; a site-wide guard test enforces it.
- **Revisit the legal texts whenever the site changes**: games (localStorage for game state, word lists), a contact form (data processing, processor agreement, Turnstile), analytics, embeds, or any new third-party service. The privacy policy must always match what the site actually does.

## Cloudflare Functions (`functions/`)

- The site is static, the only server code is the contact form API, in Cloudflare Pages Functions (`functions/api/contact.ts` and `contact-token.ts`, helpers in `functions/_lib/`). The Pages project is `leonkrix-dev`.
- `functions/` has its own `tsconfig.json` with the Workers types (they conflict with the DOM types of the Astro project), and is excluded from the root `tsconfig.json`. `pnpm typecheck` runs `astro check` and `tsc -p functions/tsconfig.json`. ESLint and Vitest cover the folder (tests next to the code, `*.test.ts`). Non-secret mail settings (SMTP host, port, account, sender and recipient) are constants in `functions/_lib/config.ts`; the only secret is `SMTP_PASSWORD`.

Locally they live in `.dev.vars` (gitignored, protected from Claude Code by a Read deny rule in the personal, untracked `.claude/settings.json`, see "Secrets and Claude Code" below); `.dev.vars.example` lists the names.

- In the Cloudflare dashboard (Settings, Runtime or Functions, compatibility flags) the flag `nodejs_compat` and the compatibility date (2026-09-29, the newest date the dashboard allowed) must be set for **both** Production and Preview before an endpoint that imports `worker-mailer` is deployed.

## Live checks and monitoring

CI checks the code before it is deployed. These look at what is actually running. Neither is part of the "CI passed" gate (they look at the live site, not at a pull request); a failure shows as a failed workflow run and GitHub sends an email.

- **Live check** (`scripts/live-check.ts`, `pnpm live-check`, workflow `.github/workflows/live-check.yml`): runs every six hours, after every successful production deployment (Cloudflare reports deployments to GitHub, the workflow reacts to `deployment_status` of the production environment) and by hand. It repeats a failed check a few times, because a new deployment needs a moment to reach every location. Checks: **custom domain** (reachable; see the bot protection note below), home page (status, title, sections), security headers (must equal the `/*` block of `public/_headers`, so there is one list), the CSP in the page, response time (warning only), stylesheet and script (served, immutable) and `og.png`, redirects (http to https, www to apex, the old German legal addresses to the new ones), legal pages (both languages, noindex, **no address placeholders, email and address not readable**), robots.txt and sitemap.xml, the custom 404, the **Uses page** (answers, has a heading, the home page links to it), **security.txt** (has a Contact line, fails when expired, warns below 60 days), the **palette data** (`/palette.json` has places, notes, projects and the Uses summary and shows no readable address), the **contact form API** (token endpoint, no CORS, cross-site and Origin-less requests refused, and a honeypot probe that proves secret, switch and KV binding are in place without sending a mail), the **TLS certificate** (fails below 14 days), the **domain registration** (RDAP lookup, fails below 30 days, warning below 60; a failed lookup is only a warning) and the **mail DNS records** (MX, SPF and DMARC must still point to IONOS). Each check returns pass, warn or fail, only a fail fails the run. A summary table is written to the workflow run page, and the README shows a badge for the live check and one for the link check (the latest run on the default branch, red when the live site has a problem). `pnpm live-check --base http://localhost:8788` checks a local `pnpm dev:functions` (without the infrastructure checks). The script has no dependencies, Node 24 runs the TypeScript file directly, and its logic is unit tested with a fake site (`scripts/live-check.test.ts`). **When a new feature changes what the live site must do (a new page, a new header, a new API endpoint), extend the live check in the same PR.**
- **Bot protection and the GitHub runners (learned the hard way):** Cloudflare's Bot Fight Mode (on, see Decisions) shows a "Just a moment..." challenge (HTTP 403, header `cf-mitigated: challenge`) to requests from data centers, and GitHub's runners are data centers, so the first manual run saw only challenge pages from `leonkrix.dev` (our own computer is not challenged). The scripts therefore detect the challenge (`isChallenge`), report the custom domain as reachable (TLS, DNS and the http and www redirects still work from the runner) and read the page content from `https://leonkrix-dev.pages.dev`, the same deployment without the bot protection (`--fallback none` switches that off). The fallback is only used when the custom domain is challenged, so a run from your own machine checks the real domain. If pages.dev were ever challenged as well, the options are to turn Bot Fight Mode off or to give up the post-deployment content checks from GitHub; Bot Fight Mode cannot be skipped by WAF rules on the Free plan.
- **Link check** (`scripts/check-links.ts`, `pnpm check-links`, workflow `.github/workflows/link-check.yml`): runs every Tuesday and finds every external link on the published pages (home page, both legal pages) and checks it (HEAD, then GET, retries, linkedin.com only warns because it blocks bots). Links are read from the pages, so new links in the content are checked automatically. A link that is on no page goes into `EXTRA_LINKS` in the script, and a new page with links goes into `PAGES` (every note, because it links to GitHub). `pnpm check-links --dir dist` checks a local build.
- GitHub disables scheduled workflows of a public repository after 60 days without any repository activity. Regular commits keep them alive; if the site is ever left alone for two months, re-enable them in the Actions tab.
- Not included on purpose: a real mail as test (it would fill the mailbox and use the rate limit), an external uptime service, log analysis. Weekly security scanning (audit, CodeQL, Scorecard) is described under CI.

## Contact form (live in production)

- Status: live. Free, no third party: the message goes through our own Cloudflare Pages Function to our own IONOS mailbox via SMTP (`smtp.ionos.de:587`, STARTTLS, `worker-mailer`, verified in a spike: about 420 ms). The IONOS plan has one mailbox, so `hello@leonkrix.dev` is sender and recipient; the visitor is Reply-To. Subject: `[leonkrix.dev] New message from <name>`.
- Why not "just Cloudflare": Email Routing (receiving) would take over the MX records and break the IONOS mailbox. Cloudflare Email Sending is Beta and paid (about 5 USD per month). Fallbacks if IONOS ever fails: Cloudflare Email Sending, Brevo or Resend, all behind the small `sendMail` interface in `functions/_lib/smtp-mailer.ts` (a new processor would need a privacy policy update).
- Fields: name, email, message. Requires JavaScript; without it (`@media (scripting: none)`) the form is hidden by CSS and the section shows the row of buttons (Email, GitHub, LinkedIn; the address is rendered by CSS and becomes a mailto link with JavaScript). The form is in the page from the start and is not shown by the script, so nothing moves when the script is ready. **Nothing in the form moves either** (checked by the layout guard): the message of a field is one short line (the texts in `src/lib/contact.ts` are short on purpose, about 28 characters at most for name and email) that sits in the gap below the field, `position: absolute`, or in the row of the counter (message); the progress ("Sending") and a problem with sending take the place of the privacy note next to the button (one grid cell with an invisible copy of the longest text, which sets the height); the confirmation lies on top of the form in the same grid cell and is as high as the form. The form has no `action` or `method` on purpose (a submit without JavaScript must not put the message into the URL).
- UI: `src/components/ContactForm.astro` (markup and page script), browser logic without DOM in `src/lib/contact-client.ts` (unit tested). The time token is requested when the visitor first focuses the form, never on page load. **Build switch:** the form (and the matching privacy policy and Impressum text) is built in only with the build variable `PUBLIC_CONTACT_FORM=true` (Astro env schema, default false). `pnpm build:form` builds with it on; the browser tests and Lighthouse use that build; plain `pnpm build` (CI build job) has no form. Production has both switches on.
- Validation rules live in `src/lib/contact.ts`, one plain TypeScript module imported by the browser script and by the Function (relative import); the server is authoritative. Limits: name 2-80, email ASCII, valid and at most 254 (64 before the @), message 20-2000 characters (counted as people see them), no control or bidi spoofing characters. Add a test with the boundary cases whenever a rule changes.
- Endpoint (`functions/_lib/contact-handler.ts`, wired in `functions/api/contact.ts` and `contact-token.ts`): `GET /api/contact-token` gives a signed time token, `POST /api/contact` checks in a fixed order (method, Origin and Sec-Fetch-Site, switch and configuration, content type, body size 10 KB, JSON, honeypot, token, validation, rate limit) and then sends one mail. No CORS, fixed recipient and sender, header injection prevented, no message content in logs, generic errors. New server behaviour needs a test in `contact-handler.test.ts`.
- Rate limit: Cloudflare KV (binding `RATE_LIMIT`), 3 messages per sender and hour, 30 in total, senders only as salted hashes, counters expire after 2 hours.
- Cloudflare configuration (set in the dashboard, there is no Wrangler file; Production and Preview are separate): Secrets `SMTP_PASSWORD` and `FORM_SECRET` (32+ random characters, signs the tokens and salts the hashes), KV binding `RATE_LIMIT` (namespace `leonkrix-contact-rate-limit`, shared by both environments), compatibility flag `nodejs_compat` and date 2026-09-29. Plain variables `PUBLIC_CONTACT_FORM=true` and `CONTACT_ENABLED=true` are set in Production and in Preview (without `CONTACT_ENABLED` the endpoints answer 503, without `PUBLIC_CONTACT_FORM` the build has no form). A changed build variable needs a new deployment. Production also has the three Impressum variables. Local: `.dev.vars` (`SMTP_PASSWORD`, `FORM_SECRET`, `CONTACT_ENABLED=true`) and `pnpm dev:functions`. The mailbox password gives access to the whole mailbox: long, unique, never logged, rotated if leaked.
- Legal: the privacy policy describes the form exactly while it is built in (see Legal). The form plus the email address are the two contact channels for the Impressum. No Turnstile (it would load a third-party script); add only if spam appears, together with a CSP and privacy policy change.
- Tests: unit tests for the shared rules, the client logic and every Function module (mocked mailer, in-memory KV), build-output tests for the switch and the legal texts, Playwright and axe tests for the UI (API mocked with `page.route`). The real mail round trip is tested by hand on a preview.

Pure logic in `logic/` (maps with typed, named rooms, about 45 clue types including neutral clues, a search solver, a second rule solver that is also the rater, the generator, the moves of the player in `play.ts`, the clue texts in `describe.ts`); skins in `data/skins.ts` and `data/words.ts` (Case file, Outage; people vs devices); the level pool `data/levels.json` (18 levels, made by `pnpm levels`, plan in `data/pool-plan.ts`, stories in `data/stories.ts`, CI gate `pool.test.ts`; the victim of a level varies). Every level must pass `problemsOf` (both solvers find exactly the stored solution); the victim never gets a clue. Random levels are made in the browser in up to four Web Workers (`components/generate.worker.ts`, sizes by tier in `logic/random-level.ts`), and a random level's address (`?level=random&seed=...`) makes the same level again. The pictures of the objects come from Lucide (`data/object-icons.ts`). Clues: every part of a clue must say something (a combination whose part follows from the other is never made), at most one row and one column clue per level, a medium level has at least half of the people placed by the clues alone (`directlySolved`), anything there is only one of is "the". An easy level is solved completely by "this person has one cell left" (`nakedSolved`). Hints (`logic/hint.ts`, `deduce` in `logic/propagation.ts`) are always the next logical step in three stages with a counter, and the last stage can explain why (`logic/explain.ts`, "Why here?" dialog). The pool is chosen from several candidates per level for an even mix of clue kinds (`logic/balance.ts`, `LEVELS_CANDIDATES` and `LEVELS_SELECT` of `pnpm levels`). Changing the generator changes what a seed gives, so old shared links of random levels then give another (equally valid) level. An object is one unit (a sofa or a cable tray over two cells: next to means beside it, not on it; directions are taken from the whole object). Next: nothing planned for this game; ideas are collected in PLAN.md (Phase 4b, the project card animations, is done; Link Up is next to be released, then Word Radar).
- **Link Up (4.4) is live** (`src/games/link-up/`, README is the source of truth). About 240 hand-written categories with more than 3,000 terms in `data/categories-*.ts` (7 to 20 terms each, every term in exactly one category, unique across the pool; definitions are our own words, at most 100 characters, without the term itself). The data is fetched in pieces: `data/catalog.ts` (generated, list of every category with its file; after a change run `pnpm exec vitest run src/games/link-up/data/catalog.test.ts -u`), `shards.ts`, `load.ts`, `generatePuzzleLazily`; `data/index.ts` imports everything and is for tests and tools only (never import it in the island: it would put all the data into the first script). A script of the game page starts the first puzzle early (`logic/first-game.ts`), in parallel with React; without that the page scores about 95 in Lighthouse instead of 96 to 98. The `conflicts` list in `data/conflicts.ts` names category pairs that must never share a puzzle (a new category whose terms could pass for another's needs an entry). `logic/puzzle.ts` makes puzzles and `countSolutions` (a separate counter) must find exactly one solution; `logic/game.ts` is the immutable game (auto-submit with the fourth pick, four mistakes, one away, a repeated wrong group is free); the React island only draws. Categories are shown only when found (or missing after a loss), term definitions appear on hover, focus or tap. `?seed=` makes the same puzzle again.

The data of English is as below. Data made by `pnpm word-radar-data` (`scripts/word-radar/`: GloVe 6B 100d and WordNet 3.0 from the gitignored `data-raw/word-radar/`, own PCA in TypeScript, 30,000 words, 64 numbers each as bytes, 1,510 hidden words, blocklist in `blocked-secrets.txt`); the three data files are committed and fetched when the page opens (about 2 MB, started by a page script in parallel with React, `data/load.ts`). The rank of every word is computed at the start of a round (`logic/similarity.ts`). GloVe and WordNet are credited in `THIRD_PARTY.md` (the WordNet notice must stay). Layout never moves (skeleton, reserved space, fixed-height list, checked by the generic layout guard).

Any new global style or script has to be paid for the same way; do not raise a budget without a reason.
- **Easter eggs** (none tracks or stores anything): a greeting in the console (`console.info`, with the link to the source), a greeting as a comment in the HTML of every page (before `<html>`; the charset must stay within the first 1024 bytes, a test checks it), the **radar** (Konami code, or the command `radar`; ignored while typing in a field), `/humans.txt` and `/.well-known/security.txt`. **The radar is useful, not only an animation** (`src/scripts/radar.ts`, `src/lib/radar.ts`, `src/styles/radar.css`): a beam turns once around the middle of the screen, every thing of the page that is worth a look and on the screen lights up with a frame and its label when the beam reaches it (the delay comes from its direction, `angleOf` and `pingDelay`), then a panel lists everything the page has as buttons that scroll there and light the thing up again (Escape or the button closes it, a second run replaces it). **What is worth a look is marked by hand** with `data-radar="Label"` on the element (the availability badge, the hero buttons, "What I am doing now", the key figures of a project and of a note, the games, the contact form and the direct contacts, the setup on the Uses page, the game itself, "Play" and "The code on GitHub" on a note, the terminal of the 404 page, and the source link and "How this site is built" in the footer, so no page is empty); nothing is guessed. **A new page or section with something the visitor should find gets a `data-radar` on it** (a label of a few words; the same label counts once). ## Decisions and rationale

- **Astro over plain React/Next.js**: static one-pager, minimal JS, React only as islands. No MERN/backend needed.
- **Cloudflare over Vercel**: free forever, unlimited bandwidth, commercial use allowed (Vercel Hobby is non-commercial only). Vercel is the fallback.
- **Git integration + branch protection over deploying from Actions**: no API tokens or deploy secrets, fewer moving parts; branch protection guarantees only CI-green code reaches `main`.
- **No Airbnb ESLint config**: unmaintained, incompatible with flat config / TypeScript / Astro. Modern strict rule sets instead.
- **No cookie banner, no analytics, no third-party embeds/CDNs**: keeps the site legally simple (self-hosted fonts, a contact form that needs no third-party service because the message goes through our own Cloudflare Function to our own mailbox).
- **All rights reserved instead of MIT**: texts, images and design should not be freely reusable.
- **Impressum address kept out of git**: injected via build variables; alternatives to a private address are a paid Impressum/c-o service (roughly 5-20 EUR/month); a fully anonymous Impressum is not legally possible (name and serviceable address are mandatory).
- **Mail stays at IONOS, DNS moves to Cloudflare**: copy the IONOS MX records before switching nameservers.
- **Games are optional fun, not the core**: MVP first.
- **CodeQL yes, SonarQube Cloud no**: CodeQL is free, GitHub-native and useful once games handle user input; Sonar would duplicate ESLint/TypeScript/CodeQL findings and adds an external service and a secret.
- **Single required check `CI passed`**: an aggregate job so new CI jobs never require changing the ruleset.
- **Live check instead of an uptime service**: `scripts/live-check.ts` looks at the published site from outside (see "Live checks"). It needs no account and no new processor, and it checks far more than "is it up". A separate uptime service was considered and not needed.
- **Private address in the Impressum, obfuscated**: see Legal. Legal pages come right after Phase 1, before design work.
- **Cloudflare baseline, not more**: Full (strict), Always HTTPS, min TLS 1.2, Bot Fight Mode (it also challenges GitHub's runners, see "Live checks and monitoring"), AI bot blocking. **Keep off**: Web Analytics (third-party script, breaks the privacy promise), Rocket Loader (rewrites scripts, conflicts with CSP), managed robots.txt (robots.txt lives in the repo). DNSSEC is deliberately not enabled (small benefit, outage risk). HSTS is sent from `public/_headers` (safe, because the whole `.dev` TLD is HSTS-preloaded anyway). Security headers live in the repo (`public/_headers`), not in the dashboard.
- **Workflow actions are pinned to full commit SHAs**: IDE inspections may flag their inputs as undefined (false positive, the IDE cannot resolve metadata for SHA refs).

## Conventions

- Small, focused commits with Conventional Commit messages.
- Never push to `main` directly: work on branches, open PRs, CI must pass, then merge.
- Prefer editing existing components over adding new abstractions. Keep components small and typed.
- Do not add third-party scripts, fonts, or embeds without checking the legal section above.
- Never put invisible or bidirectional control characters literally into source files; write them as escapes in strings (a repository guard test checks this). Beware: some tooling converts an escape sequence typed in a comment into the real character, so describe such characters in words (for example "U+202E").
- Before opening a PR run `pnpm check` locally.
- **Test cadence while building a feature** (decided with Leon, 2026-10-15): the full suites take long (`pnpm check` about two minutes, `pnpm test:e2e` about two, `pnpm lighthouse` about five, three runs on every page), and waiting for them several times per feature wastes the most time. So: build the feature, run only what is quick and relevant (the tests that were just written or touched, `pnpm exec vitest run <file>`, `pnpm exec playwright test <file>`, `pnpm lighthouse --page /path/` for one page, lint and typecheck), show it to Leon and take his feedback, build the changes. Only when Leon gives his final okay run **everything once** (`pnpm check`, `pnpm test:e2e`, `pnpm lighthouse`) and fix what the full run finds. Do not run the full suites after every round of feedback. Exception: a change that touches shared code (global styles, layouts, the layout guard, the page list) deserves one full run before the okay, because a failure there can be far from the change.
- The PR title becomes the squash commit message: write it as a Conventional Commit (`feat: ...`, `fix: ...`, `chore: ...`, `docs: ...`, `ci: ...`).
- Commit locally as often as you like, but push a branch only when the feature is complete (each push builds a Cloudflare preview).
- New external links use the `ExternalLink` component (`target="_blank"`, `rel="noopener noreferrer"`).
- In the WebStorm commit dialog, "Analyze code" is off (lint-staged and CI already cover it); `dist/` and `.astro/` are marked as excluded.
- **Keep the portfolio in sync with the tooling:** when a new test or quality tool is added to this site (e.g. Playwright, axe, Lighthouse CI), add it to the technology registry in the "Code Quality" group and to the `technologies` of `src/content/projects/website.yaml`. Update the website project highlights or key figures when they become verifiable (e.g. a Lighthouse score).
- **Keep the whole portfolio current, not just tooling:** whenever the site gains or changes a feature, update in the same PR (1) the technology registry and the "Code Quality" group, (2) the project entries in `src/content/projects/` (highlights, technologies and key figures, e.g. the number of automated tests, Lighthouse score), (3) the About text and any claim such as "no third-party service", (4) the privacy policy and Impressum (they must match what the site does, see Legal), (5) README, PLAN.md and this file. If a new feature needs a decision (legal, costs, third parties), ask Leon before building it.
